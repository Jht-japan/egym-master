## テーマ: 判断①（RLS厳格化後の書き込み経路）の解決 — `tighten-rls.sql` 更新

対象ファイル: `file6/supabase/tighten-rls.sql`（SQLのみ。HTMLの変更は無し）
関連: 技術仕様書 §11 判断①（✅解決済みに更新）、`SETUP_CHECKLIST.md` step6

### 背景（何が問題だったか）
- 認定・招待は**クライアントから直接 `trainers` を書き込む**設計（既存の super/facility と同じパターン）。
- 当初の `tighten-rls.sql` は `trainers` の INSERT/UPDATE を **super と facility 管理者のみ**に許可していた。
- そのため RLS を適用すると、以下が **すべて失敗**する状態だった:
  1. Star2 が Star1 を招待（`trainers` に star1 行を insert）
  2. Star3 が Star2 を招待（star2 行を insert）
  3. Star2 が Star1 を認定（該当 star1 行を `status='certified'` に update）
  4. Star2/Star3 が「育成」タブで候補者一覧を取得（`mentored_by=自分` の行を select）
     ← select も super/facility/本人のみ許可で、メンターは自分の候補者すら見えなかった。

### 決定（option B を採用）
Edge Function 経由（option A）ではなく、**RLSポリシーで該当経路をロール別・最小限に許可**する方針。
「他人の候補者・他施設」は不可に厳密スコープし、無条件の全許可にはしない。

### 変更内容（`tighten-rls.sql`）
- **補助関数追加** `public.has_role(text)`: ログイン中ユーザーが指定 role を持つか判定（security definer）。
- **`tr_select`**: 条件に `mentored_by in (my_trainer_ids)` を追加 → 自分の候補者を閲覧可。
- **`tr_insert`**: 以下 2 経路を追加（どちらも `mentored_by=自分` かつ `facility_id=自施設`）:
  - `star_level='star1' and has_role('star2')` … Star2→Star1 招待
  - `star_level='star2' and has_role('star3')` … Star3→Star2 招待
- **`tr_update`**: `star_level='star1' and has_role('star2') and mentored_by in (my_trainer_ids)` を
  using / with check の両方に追加 → **Star2 が自分の Star1 のみ認定可**。
  ★ star1 限定にしたことで **Star3 は Star2 を更新できない＝「監視のみ」仕様を維持**。
- **`cr_select`**: `trainer_id in (my_trainer_ids)` を追加 → 申請者本人が自分の申請状況を閲覧可。
- ヘッダcoメント・「動作確認」節に Star2/Star3 の観点を追記。

### セキュリティ上の担保
- すべて `to authenticated`＋ロール/関係（`mentored_by`・`facility_id`）で限定。未ログインでは何も読めない/書けない。
- メンターは「自分が担当し、かつ自施設」の候補者にしか触れない（他人の候補者は insert/update/select 不可）。
- `user_roles` は従来どおりクライアント直接書き込み不可（招待・昇格・削除は service role の Edge Function）。
- 補助関数は security definer（テーブルオーナー実行）のため、ポリシー内の `trainers` 参照で
  RLS 再帰は発生しない（既存 `my_trainer_ids` 等と同じパターン）。
