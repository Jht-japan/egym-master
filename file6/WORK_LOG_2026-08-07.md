# 作業ログ 2026-08-07 — 認定フォールバック＆施設昇格（メンター未割当対応）

## 目的（オーナー依頼）
新規ジムでは最初 Star2・Star3 が居ないため、Star1 の認定を誰も行えなかった。
**「認定はメンター（自分を割り当てた人）が行う。メンターが居なければ施設アカウントへフォールバックし、
施設が認定→上位レベルへ昇格させてチェーンを立ち上げる」** というルールに統一した。

## 決定した仕様（統一ルール）
- 認定の宛先は `trainers.mentored_by`（担当メンター）で決まる。
  - **Star1**: 担当 Star2 が居る → Star2 が認定（従来のハンドシェイク）。居ない → **施設**へ申請（新規）。
  - **Star2**: 担当 Star3 が居る → **Star3 が認定（新規ハンドシェイク）**。居ない → 施設へ申請（従来どおり）。
  - **Star3**: JHTJapan（変更なし）。
- 施設は **認定済みトレーナーを同一アカウントのまま昇格**できる（Star1→Star2, Star2→Star3）。
  新規ジムのチェーン構築用（オーナー決定=「Promote in place」）。

## 変更ファイル
### `egym_star1_app.html`
- `SELF` に `mentored_by / facility_id / cert_req_sent` を追加。`loadProgress` で格納。
- メンター未割当時は `cert_requests` を確認して申請済み表示を復元。
- `sendCert()` を async 化：メンター有り＝従来トースト通知のみ／メンター無し＝`cert_requests`（pending）を実挿入（重複ガード付き）。
- 認定タブの文言（達成カード・フロー手順・申請モーダル）を「担当スター2」⇄「施設管理者」で出し分け。

### `egym_star2_final.html`
- グローバル `MENTORED_BY / MENTOR_NAME` を追加。`loadProgress` で担当スター3を解決。
- 認定達成カードを分岐：担当スター3有り＝`notifyMentor()`（ハンドシェイク通知のみ）／無し＝従来の `applyToFacility()`（施設へ `cert_requests`）。

### `egym_star3_app.html`
- 担当スター2候補者に対する認定ハンドシェイクを新設：候補者カードに条件達成で「スター2認定」ボタン、
  確認モーダル、`doCertify()`（`trainers.status='certified'` + pending の `cert_requests` を approved 化）。
- 「監視のみ」だった注記を、条件未達の案内へ変更。

### `egym_facility_app.html`
- `loadAllData` に `mentoredBy` を追加。
- 認定済み Star1/Star2 の行に「↑昇格」ボタンを追加。`promoteTrainer(id)` を新設
  （`trainers` の star_level 更新＋進捗リセット → Edge Function `promote_role` で user_roles 切替）。
  ※super の `promoteTrainer` と同じ挙動。Star1 の申請は既存の `approveCert` がそのまま認定。

### `supabase/tighten-rls.sql`
- `tr_update` ポリシーに **Star3 が担当 Star2 を更新できる**句を追加
  （`star_level='star2' and has_role('star3') and mentored_by in my_trainer_ids()`）。
- ⚠️ **本番へ再適用が必要**（Phase 4）。未適用だとセキュリティ有効化後に Star3 の認定が失敗する。
  Star1→施設の申請挿入は既存 `cr_insert`、施設の昇格（star_level 更新）は `is_facility_admin` で既に許可済み。
